agents (`hospital/crew/README.md`); the insurer's seven agents are CrewAI agents with `VerificationFlow` and `QueryFlow`

## 2. Gaps

### Gap 1 (critical): CrewAI is not used

Evidence:
- `docs/DECISIONS.md` (2026-10-07, crew service): "The `crewai` package is not installed ... Agents are plain classes".
- `docs/demo/02-HOW-IT-WORKS.md` §3: "There is no CrewAI library in this project."
- `docs/dev-b/PROGRESS-DEV-B.md`: "No CrewAI dependency (single structured call per agent)".
- Neither `hospital/crew/pyproject.toml` nor `insurer/crew/pyproject.toml` lists `crewai`; `uv.lock` has no `crewai` entry.
- Orchestration is code, not agents: `hospital/crew/crew/main.py` hard-wires each job type to one handler; the insurer
  verification order lives in `insurer-api` (`E2E_ORCH=inline`) or in n8n flows 10-16 (`E2E_ORCH=n8n`). Each "agent" is
  one prompt + one JSON call (`insurer_crew/agents.py`, `hospital/crew/crew/agents/*.py`).
- By default the full end-to-end run does not call the insurer crew at all: `scripts/e2e_full.py` has
  `E2E_CREW=off` ("rules only") as its default.
- Not built at all: hospital `classify-extract` and `supervise` LLM jobs (DECISIONS.md: "not built").

What helps the migration: both crews sit behind stable HTTP surfaces (hospital `/v1/jobs/*`, insurer
`/v1/{identity,authenticity,coverage,...}`), and the APIs validate whatever comes back. CrewAI can be put behind those
endpoints without changing hospital-api, insurer-api, n8n or the UIs.

### Gap 2: no single command

A demo today needs Docker and Ollama running, then `make init`, `up-infra`, `up-insurer`, `up-n8n`, `up-insurer-n8n`,
`up-rag`, `seed-kb`, `migrate`, `seed`, `migrate-insurer`, `seed-insurer`, a separate terminal for `make run-rag`, and
finally `make e2e-full` with env flags (`E2E_CREW=ollama`, `E2E_ORCH=n8n`). `scripts/e2e_full.py` already starts several
host services itself, which is a good base for one command. The runbooks contain a personal path
(`docs/demo/01-RUNBOOK.md:13`, `docs/demo/04-INSPECT-AND-RUN.md:7`: `/home/ashok/Downloads/...`).

### Gap 3: problem statement not fully covered

### Gap 4: demo and viva risks

- Weight: 20 services in `infra/compose/*.yml` (the plan document says 23); 16 GB RAM minimum. Only the `hospital-api`
  Dockerfile was build-tested; the demo runs services on the host.
- Speed: the real-model hospital e2e took about 7 minutes, ~5 of them on one query draft (`HANDOVER.md`).
- Course tooling: no Flowise, Pinecone or LangSmith (uses Qdrant and Langfuse). Defensible, but prepare the reason.
- Repo hygiene: committed `services/tpa-sim/data/tpa_sim.db` and `docs/implementation.zip`; a two-line `README.md`.

### Gap 5 (new, found while testing the install): dependency conflict

Dry-run resolution of `crewai[litellm]==1.15.23` (latest on PyPI today) in this uv workspace succeeds but:
- **downgrades `pydantic` 2.13.5 → 2.12.5 for the whole workspace** (crewai pins `pydantic<2.13`), so every package's
  tests must be re-run after adding it;
- adds about 100 packages (chromadb, lancedb, litellm 1.104, opentelemetry, openai 2.x, etc.);
- needs Python `>=3.10,<3.14` (repo uses 3.12+; fine on 3.12/3.13, not on 3.14).

This is the "large dependency tree" Sohail avoided. Keep it confined to the two crew packages and pin the exact version.

## 3. Target design

Rules:
1. **Deterministic code stays the authority.** Calc engine, verification engine, completeness rules, validators,
   PII guard, grounding guard, supervisor checklist and repair whitelist are wrapped as CrewAI tools or task guardrails.
   An agent may explain or map; it never decides a number or a gate.
2. **Flows own order and state; crews do the work.** Each side gets a CrewAI `Flow` (`@start`, `@listen`, `@router`)
   with a Pydantic state model. Crews inside are `Process.sequential` (no hierarchical manager, so no `manager_llm`
   needed).
3. **APIs stay the boss of persistence.** Crews return Pydantic objects; the API validates and stores them (unchanged).
4. **Offline safety net stays.** `CREW_LLM=rules` keeps a deterministic path that runs the same Flow with a stub LLM.

### 3.1 Hospital side: `HospitalClaimFlow` (in `hospital/crew`)

| Flow step | Crew / agents | Tools (existing code reused) | Output |
|---|---|---|---|
| `@start load_case` | none (plain step) | `crew/api_client.py` → `/v1/internal/cases/{id}/build-context` | `CaseState` |
| `@listen intake` | **Document Crew**: Intake Agent | doc-pipeline client (parse/classify/mask), vision-service client (quality, stamp), PII guard `guards/pii.py` | typed extracts per document |
| `@listen validate` | **Validation Crew**: Completeness Agent, Consistency Agent | completeness rules from hospital-api, ICD lookup (port `insurer_crew/tools.py:icd_lookup`), bill arithmetic (`tools/numbers.py`) | findings list |
| `@listen estimate` (new, Gap 3) | **Policy Estimate Crew**: Coverage Agent | rag-service search, `calc_engine` as a tool | admissible-amount estimate with citations |
| `@listen build` | **Claim Builder Crew**: Builder Agent, Critic Agent | `tools/assemble.py`, `tools/categories.py`, `category_map.yaml`; guardrails `guards/supervisor.py` + `check_repair` whitelist | claim draft + readiness score |
| `@router route` | none | blocker rules | `"needs_info"` → n8n notifies desk; `"ready"` → officer approval (human in the loop, unchanged UI) |
| `QueryFlow` | **Query Crew**: Triage Agent, Draft Responder Agent | `agents/responder.py` category defaults; guardrail = `guards/grounding.py` G01-G08 | triage result, grounded draft |

The existing job types map onto Flow entry points: `claim-build`/`claim-repair` → `HospitalClaimFlow`,
`query-triage`/`query-draft` → `QueryFlow`. `crew/main.py` keeps `/v1/jobs/*` and calls `flow.kickoff_async(inputs=...)`.

### 3.2 Insurer side: `InsurerVerificationFlow` (in `insurer/crew`)

| Existing function (`insurer_crew/agents.py`) | CrewAI agent | Crew | Kept as tool / guardrail |
|---|---|---|---|
| `identity` | Identity Agent | Verification | `tools.compare_names`, `normalise_name`; code `enforce` → guardrail |
| `authenticity` | Authenticity Agent | Verification | `_signals`, `get_bill_arithmetic`, `find_duplicates` |
| `coverage` | Coverage Agent | Verification | `RagClient.search`, `_keyword_clauses`, `validators.quote_in` guardrail |
| `calc_mapper` | Calc Mapper Agent | Verification | `keyword_map`, `calc_engine` (final money authority) |
| `supervisor` | Supervisor Agent | Verification | `_has_blocker` guardrail (cannot downgrade to proceed) |
| `query_drafter` | Query Drafter Agent | Query | `strip_forbidden`, `reject_payables`, `neutralise` guardrails |
| `triage` | Triage Agent | Query | rule defaults |

Keep the seven HTTP endpoints so insurer-api and n8n flows 13-16 work unchanged; each endpoint runs a one-task crew
for that agent. Add one new endpoint `/v1/verification/run` that runs the whole Flow, used when `INS_ORCHESTRATOR=crew`.
Keep `runtime.py` (concurrency gate, idempotency cache, Langfuse tracer, prompt registry) and `app.py` auth unchanged.

### 3.3 Cross-cutting implementation notes

- **LLM.** `crewai.LLM(model="ollama/gemma4:latest", base_url="http://localhost:11434", temperature=0)`. Wrap it in a
  small `BaseLLM` subclass (or a call hook) that runs `assert_no_pii` before every call, so the DPDP guard still sits
  in front of the network.
- **Structured output.** `Task(output_pydantic=...)` using the existing schemas in `insurer_crew/schemas.py` and the
  contract models.
- **Guardrails.** `Task(guardrail=fn, guardrail_max_retries=2)` where `fn(output) -> (bool, value_or_error)` calls the
  existing guard. This replaces the hand-written "regenerate with feedback" loops.
- **Small-model tool calling.** `gemma4`/`llama3.1:8b` are weak at multi-step tool use. To keep the demo reliable, the
  Flow precomputes deterministic tool results and passes them as task context; agents get at most 1-2 tools each,
  `max_iter` 3, `allow_delegation=False`.
- **Memory/knowledge off.** `Crew(memory=False)`, no `knowledge_sources`: both default to OpenAI embeddings. Retrieval
  stays in rag-service.
- **Telemetry off.** `CREWAI_TELEMETRY_OPT_OUT=true` and `OTEL_SDK_DISABLED=true` in `.env.example`, both Dockerfiles
  and the Makefile env (insurer Dockerfile already sets them).
- **Audit.** `step_callback`/`task_callback` on each crew append an event to the existing hash-chained audit trail.
- **Tests.** Existing tests stay; agent calls are faked through a stub `BaseLLM` (replacing `FakeLLM`).
- **`crewai run`.** Add `[tool.crewai] type = "flow"` and a `kickoff()` entry in each crew package so `crewai run`
  demos one side on its own.

### 3.4 What does not change

hospital-api, insurer-api, database schemas, n8n flow logic (triggers, webhooks, reminders, wait nodes), UIs, contract,
doc-pipeline, vision-service, rag-service, tpa-sim, calc engine.

## 4. Single command

- `make demo`: checks Docker, Ollama and RAM; pulls missing models (`gemma4:latest`, `nomic-embed-text`); runs
  `init-secrets`; starts containers in order with health waits; migrates and seeds both databases and the knowledge
  base; starts host services in the background with logs in `.e2e-logs/`; runs `e2e_full.py` with
  `E2E_CREW=crewai E2E_ORCH=n8n`; prints the evaluation report; `make demo-down` stops everything.
- `make demo-offline`: same run with `CREW_LLM=rules` (no model), about 1-2 minutes. Viva backup.
- Implemented as `scripts/demo.py` (one Python driver, reusing `e2e_full.py`'s service starter) rather than a long shell
  script, so it works the same on every team laptop.
